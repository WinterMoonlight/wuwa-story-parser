# 阅读状态与覆盖报告

批量导出生成`主线阅读报告.md/json`和`覆盖报告.md/json`。两者用途不同：阅读报告描述TXT中实际展示的内容；覆盖报告记录全部提取材料、引用、条件与缺口。

## 阅读状态

|状态|含义|
|---|---|
|`ordered_draft`|按已采用的配置依据形成有序草稿，未自动等于人工验收通过|
|`ordered_draft_with_gaps`|已有主干，但含缺口、略过过程或局部未定位内容|
|`local_fragments_only`|每段内部可读，尚未证明它们组成完整任务的先后顺序|
|`no_ordered_body`|尚无可交付的有序正文|

当前主线数量和未解决任务见[当前状态](status.md)，不在本页重复维护批次数字。

## 如何看JSON

- `counts`按确定路线、候选分支、失败结局和未核验内容统计出现次数，并非唯一台词数或完整率。
- `source_counts`说明正文、回顾、局部片段、资料及其他入口各自提取了多少。
- `order`记录配置顺序、引用关联和运行时核验范围。
- `gaps`列出缺失流程、未知动作、未确认顺序等问题；部分是资产后置或已保留的非阻塞说明。
- `mainline_reading`保存TXT的显示内容及来源指针。原始数据仍在同一JSON其他字段中。

`strict_pass`采用更严格的整任务支持标准，不是阅读可用率。严格解析失败、已有局部正文、已恢复回顾主干可以同时出现。

## 对照修复前后结果

使用`scripts/audits/`的相关检查程序，至少核对输入数据库哈希、原始事件和选择、未修改任务TXT、来源指针及新增片段的顺序范围。专项脚本有自己的适用条件，不应把某一轮的断言当成所有版本的通用规则。

回顾与任务调用冲突时，优先使用明确任务依赖；仍缺证据的内容保留说明。更细的规则见[语料格式](corpus-format.md)和[阅读验收](reading-acceptance.md)。
