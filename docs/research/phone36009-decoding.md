# 《幽客销残声》文本误报与手机36009解码

## 原“缺失正文”实际是控制节点

Flow_936000004_147位于“剧情_3_6_后日谈2_4_1”的TalkItem 0。节点Type=Option，PlotLineKey为空，没有TextId，也没有选项；包含图标BackgroundConfig和Wait 2.5动作。遍历现有简中文本数据库没有发现对应正文。

同库大量相同结构说明Option不仅是有选项的菜单，也用于无台词演出控制。原option_container误把“必须含非空Options”作为必要条件，导致残留TidTalk被当成旁白文字引用。本轮按Type=Option、空PlotLineKey且无TextId识别控制容器，是否含Options不再影响；有TextId或非空PlotLineKey的条目继续按文本处理。

没有编造或替换一条“找回的对白”。原节点、TidTalk、图标和Wait动作仍保存在JSON及动作记录，TXT不再出现假缺失占位。独立静态文本清单也使用同一判定，避免报告继续误报。

## 手机字段纠正

|源表/字段|正确用途|证据|
|---|---|---|
|shortmessage字段0|消息ID|36009|
|shortmessage字段1|ChatPartnerId整数|36009→72→清宵；全库299条均能关联chatpartner|
|shortmessage字段2|字符串向量形式的流程引用|剧情_3_6_后日谈生态、2、1|
|chatpartner字段4|联系人名称文本键|SMC_Name_72→清宵|

字段1不是消息类型。整数72恰好还能被错误当作偏移读出字符串“2”，这是误用类型造成的巧合，不是另一套布局。旧代码限定字段1=3也没有依据。

字段9不应作为联系人整数向量。本例该区域可读成字符串“0”，误用整数向量会得到ASCII值48；这导致旧样本32010错误关联联系人48/赞妮。正确关联是字段1=3→chatpartner3/洛瑟菈，也与手机正文WhoId解析一致。字段9的业务含义本轮不猜测。

原始消息BLOB、字段来源和哈希仍保留；联系人/流程记录必须唯一，缺失或重复继续拒绝，不使用模糊名称匹配。原“未知消息布局”的判断对36009已被纠正。
